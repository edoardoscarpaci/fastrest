# Typed client code generation — cross-repo

When the peer service's Python package isn't (or shouldn't be) importable
from your repo — a different team, a different language stack calling in,
strict repo isolation — export a portable `ServiceContract` and generate a
typed client from it. No import of the peer's router class anywhere in your
dependency tree.

See `technical_docs/features/portable-contracts.md` for the full format
reference, the `$ref`/versioning rules, and the CI `--check` recipe. This
page is the practical how-to.

## 1. Export the contract (in the producing service's repo/CI)

```bash
varco export-contract myapp.routers:OrderRouter -o order.contract.json \
    --service-name orders --service-version 2.3.0
```

`order.contract.json` is a plain JSON file — frozen route/param/schema
descriptions, no Python objects. Commit it into the **consuming** repo (that
is what decouples the two codebases).

## 2. Generate a typed client module (in the consuming repo)

```bash
varco gen-client -c order.contract.json -o order_client.py --class-name OrderClient
```

```python
from order_client import OrderClient

client = OrderClient("https://orders.internal")
order = await client.read(order_id)
await client.cancel(order_id, reason="oos")  # real, typed keyword arguments
```

Every method's signature — including custom `@route` endpoints — is built
through `build_client_method()`: the body parameter (if any) is positional,
everything else is keyword-only, and calling with an undeclared kwarg raises
`TypeError` immediately (this is the intended break vs. the old, permissive
`**kwargs: Any` pass-through — see the migration note,
`technical_docs/migrations/009-reliability-and-integration.md`, item 5).

## Or: a one-liner, no generated file at all

```python
from varco_fastapi.contract.runtime import contract_client

client = contract_client("order.contract.json", "https://orders.internal")
order = await client.read(order_id)
```

`contract_client()` builds the exact same typed methods at runtime — good
for scripts and notebooks where checking in a generated `.py` file is
overkill. Both paths go through `build_client_method`, so they cannot
diverge from each other.

## 3. Or: just the `.pyi` stub, for an existing `client_for()` call site

```bash
varco gen-client-stubs -c order.contract.json -o order_client.pyi
```

Gives mypy/your IDE real static types for a `client_for()`-built client
without checking in a full generated module. Regenerate whenever the
contract changes — CI drift check:

```bash
varco gen-client-stubs myapp.routers:OrderRouter -o order_client.pyi --check
# exit 1 if the checked-in .pyi is stale relative to the current router
```

## ⚠️ Important: this typed surface is NOT (yet) what `client_for()` returns

Read this before assuming parity with the in-process client. `client_for()`
(the everyday, same-repo/monorepo path — see `docs/client.md`) still builds
its custom-route methods through the pre-Plan-009
`custom_method(self, **kwargs: Any)` closure, **not** through
`build_client_method`. Only the code generated by this page's tools
(`gen-client`, `gen-client-stubs`, `contract_client()`) gets the new typed,
keyword-only, `TypeError`-on-wrong-kwarg behaviour today.

Practical consequence: if you call the *same* router both via
`client_for(OrderRouter, url)` (in-process) and via a
`gen-client`-generated `OrderClient` (cross-repo) for a custom `@route`
method, the two clients currently accept slightly different calling
conventions for that method — the generated one is strict/typed, the
in-process one is permissive. This is a known, plan-acknowledged gap
(the `_VarcoClientMeta` rewrite was deliberately deferred as the
highest-blast-radius part of this feature) — see
`technical_docs/features/portable-contracts.md`'s status note and the
migration note's item 5 for the tracking detail.

## What's checked by tests, and what isn't

`varco_fastapi/tests/test_contract_codegen.py::test_signature_parity` and
`varco_fastapi/tests/test_client_typed_routes.py::test_resolver_parity` are
the two load-bearing tests enforcing that `gen-client` output and
`contract_client()` output stay identical to each other for the same route —
**not** that either matches `client_for()`'s current in-process methods (see
above). Do not delete either test; they are named explicitly in the plan's
Verification section as the enforcement mechanism for the "same typed
surface" guarantee this feature otherwise only aspires to.

## Unsupported schema shapes

The hand-rolled JSON-Schema → Pydantic emitter (`contract/codegen.py`)
covers object/array/scalar/enum/`$ref`/nullable/`oneOf` — the whole set
varco itself emits. Anything outside that degrades to `dict[str, Any]` with
a `# TODO: unsupported schema` comment in the generated source — honest and
visible rather than a silent wrong type. The `schemas` block is
OpenAPI-`$defs`-shaped, so `datamodel-code-generator` remains a valid escape
hatch for anything this emitter can't represent.
